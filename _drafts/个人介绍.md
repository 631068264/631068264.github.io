# 项目经验介绍

我们当时做 Triton Server 项目，主要是想把原来分散的模型部署方式统一起来，提高推理性能和后续模型的接入效率。

在项目验收方面，我们主要关注两个维度。

**第一是结果正确性。**

因为模型需要转换格式，所以我们会用算法部门提供的原始服务和测试集做对照，验证转换后的模型输出是否符合要求。当时我们使用的相似度指标，验收要求大概是 99%。

**第二是性能和资源表现。**

我们会做不同并发量下的压力测试，对比原服务和 Triton 服务的吞吐量、延迟以及资源消耗，确认性能提升的同时不会引入严重的资源问题。

项目刚开始是逐个模型推进的，中间确实遇到过一些问题。



## 遇到问题

比如有一次，转换后的模型出现了比较大的输出误差，同时在高并发测试中也发现资源消耗异常。发现问题以后，我重新评估了修复工作量和交付风险，协调算法部门补充验证数据，同时安排团队优先处理影响上线的关键问题。后来我们排查后决定调整模型格式，好在整体部署框架不需要跟着大改。

不过这个过程也暴露出一个问题：我们比较依赖算法部门提供原模型、测试集以及协助验证，但他们本身也有其他项目，协调起来比较耗时间。

最终这个项目比原计划延期了大概一周，不过后面解决了这些问题，验收结果也达到了要求。



## 解决方法

当时 Triton Server 项目主要由我和另外一位同事负责，团队其他成员也有各自的项目任务。

我主要负责整体技术方案和项目推进。

在开发和测试过程中，我发现模型转换之后存在比较明显的输出误差，同时高并发测试时资源消耗也出现了异常。

当时我判断这些问题会影响最终验收，所以提出了调整模型格式的解决方案。好在我们原来的服务架构不需要大改，主要是调整模型格式和重新验证。

不过修复和验证都需要时间，而且还需要算法部门配合提供原始模型、测试集，以及一起分析验证结果。

所以我重新评估了工作量，认为原来的交付时间已经不太现实，就主动提出延期大概一周，并和算法部门沟通了原因、解决方案和新的时间安排。

**人员安排方面**，因为项目主要就我们两个人负责，所以我们先把需要解决的问题拆分开，各自负责一部分。

在推进过程中，我定期检查两部分进展，判断某一部分已经影响关键交付节点，再调整工作安排。发现另一部分的进展相对慢一些，参与进去一起解决问题。

最后项目虽然比原计划延期了一周，但我们把关键问题都解决了，后续测试和验收也达到了要求。



**怎样评估**

当时我们评估延期时间，主要是根据剩余需要迁移的模型数量，以及前面已经完成的模型接入和验证经验来估算的。

因为前面已经陆续接入过一些模型，所以大概知道每个模型从格式转换、部署到验证需要多少工作量。再结合当时发现的兼容性和性能问题，我们判断整体还需要一周左右。



**怎样兜底**

**原来的模型服务一直可以正常运行，所以新服务即使延期，也不会直接影响现有业务使用。**

当时我们更关注的是迁移之后的模型结果是否一致，以及性能和稳定性能不能达到要求，所以没有为了赶进度跳过验证。

另外，这个项目比较麻烦的地方是跨部门配合。

因为不同模型有各自的负责人，我们需要逐个联系算法同事，确认原始模型、测试集以及结果评估方法。

算法部门本身也有其他项目，所以我们没有一直等他们把所有材料准备好才继续。

实际推进时，我们会一边运行已有模型的验证脚本，一边联系下一个模型的负责人，提前确认测试数据和评估方式，尽量把沟通和验证过程穿插起来，减少空等的时间。

最终项目比原计划晚了大概一周，但现有业务没有因此中断，模型迁移也完成了验收。

后面我们还要和上游部门进行联调，看看实际使用的时候有没有新的问题，再根据反馈继续完善。

# **技术冲突**

**我会要求他们从相同的维度分析各自方案的优缺点。**

比如实现成本、需要投入多少人、开发周期、性能、稳定性、后续维护成本，以及可能遇到的风险。

同时，我也会结合团队成员以前的技术经验，判断大家对相关技术的掌握程度，以及项目本身的紧急程度。

**如果是已经上线的老项目，我通常会更关注稳定性和改造风险。**

如果是一个全新的项目，交付时间也比较充裕，那就可以适当考虑新技术。

但如果新框架确实有明显优势，我们也可以先做一个小范围的验证，确认收益和成本，再决定是否采用。

**在综合评估之后，如果属于我负责的技术决策范围，我会给出最终方案，并向团队说明选择依据。**

如果有人不认可，我会先听听他是不是还有其他技术风险没有考虑到。

如果有新的有效证据，我们可以重新评估。

如果只是技术偏好不同，我会充分解释为什么当前项目选择这个方案，也允许大家保留不同意见，但确定方案之后，还是需要按照统一的方向推进。

后续我也会明确任务分工和关键节点，跟进实际实施效果。

**我的原则是，技术讨论可以充分，但不能无限争论。最终还是要围绕项目目标、技术风险和交付结果来做决策。**



# 线上炸了

如果 AI 推理服务上线之后突然出现大量请求失败，我首先**会判断故障的影响范围和严重程度。**

比如先看监控指标、错误日志和链路追踪，确认是所有请求都有问题，还是某些模型或者接口出现异常，同时检查最近一次发布的变更。

**如果问题影响比较大，我会优先考虑恢复服务，而不是一定要先查清楚所有原因。**

比如问题比较明确，能够快速修复和验证，我会考虑 Hotfix。

但如果短时间定位不了，或者修复风险比较高，而且确认回滚是安全的，我会优先协调运维回滚到之前的稳定版本。

如果没办法直接回滚，就考虑先降级或者切换流量，保证核心业务能够继续使用。

**团队安排方面，我会让大家根据各自擅长的方向分工处理。**

比如有人负责分析日志和代码，有人检查部署和资源情况，有人负责准备回滚和验证。

我自己会负责综合判断问题的严重程度，协调相关人员，并决定下一步采用什么处理方案。

**沟通方面，我会及时在项目群里同步故障的影响范围、当前处理措施以及恢复情况。**

如果业务方一直追问什么时候能恢复，我会尽量给出有依据的判断。如果暂时无法确定，我也会说明目前的进展和下一次同步的时间，而不是随便承诺。

**故障恢复以后，我会组织复盘。**

主要分析为什么会出现这个问题，为什么测试阶段没有发现，哪些监控或者发布流程需要完善。

如果是测试覆盖不足，就补充相关测试；如果是发布过程的问题，就优化发布和回滚流程。

最后把改进事项落实到具体负责人，并跟进完成情况，尽量避免同类问题再次发生。

我的原则是，**线上故障先止损、再定位根因，恢复以后还要推动改进，而不是修复完就结束。**







**承担自己应该承担的责任**

- 确认线上问题已经得到处理，业务恢复正常。

- 向上级和相关业务负责人解释，当时为什么会选择这个技术方案。

  - **比如是不是高并发场景测试不够完整，或者只关注了性能提升，没有充分验证稳定性。**

- 对于团队，我也会组织大家一起复盘，分析从方案评估、开发测试到上线，哪些环节还存在不足。

  **后续最重要的还是落实改进。**

  比如增加相关场景的压力测试和稳定性验证，对风险比较高的技术变更，先进行小范围验证，再逐步上线，同时准备好回滚或者降级方案。

  对于业务方和上级，我会说明具体的改进措施，以及后续怎么验证这些措施有没有效果。

  **我觉得作为技术负责人，做决策就要承担相应责任。出了问题不能只解释原因，更重要的是把问题解决，并且让后续的技术决策和上线过程更加可靠。**

# 越级

**我会先找他单独沟通，了解他为什么选择直接向上汇报。**

如果只是一般的技术分歧，我会希望他先和我讨论，或者直接在团队的技术评审会上提出问题。

这样大家可以一起分析，也能避免不同的信息直接传到上级那里，造成不必要的误解。

但如果涉及比较严重的技术风险，我也不会限制他正常向上反馈。

**对于他提出的技术问题，我会让他提供具体的方案和判断依据。**

比如现有方案有哪些问题，他建议怎样改进，新方案的成本、风险和收益分别是什么。

然后我会结合项目情况进行评估。

如果他的方案确实更好，我会接受，也会在团队和上级面前明确认可他的贡献。

**如果他在这个方向确实很有能力，我甚至会考虑让他负责相关模块的技术设计和推进。**

因为我觉得技术负责人不需要在每个领域都是团队里技术最强的人，更重要的是能够把合适的人放在合适的位置。

当然，团队也需要有基本的协作方式。技术讨论可以充分，但最终方案明确以后，大家还是需要按照统一的目标推进。

**我更希望通过客观的技术判断和合理分工来建立团队信任，而不是单纯依靠职位来要求大家服从。**



# 工作平衡



**我会先听听他的想法，再和他解释为什么需要这些协作。**

**在任务安排上，我还是倾向于人尽其才。**

**另外，如果项目过于依赖他一个人，我会考虑逐步降低这种风险。**

比如让他组织技术分享，介绍核心模块的设计思路和常见问题。

同时也可以安排其他成员参与 Code Review，或者通过一些小任务逐步熟悉相关模块。

这样既能发挥他的技术优势，也能让团队其他人具备一定的维护能力。



因为我本身比较倾向于根据每个人的技术能力和擅长方向来安排工作，也就是人尽其才。

**但这不代表技术能力强的人，就可以不用承担任何团队协作责任。**

**如果经过评估，我认为目前的分工是合理的，我也会向团队解释判断依据。**

我也会考虑团队成员的成长意愿。如果其他同事希望参与更有挑战性的技术开发，我也愿意根据他们的能力和项目情况，逐步安排合适的任务。



# 离职

**单独沟通，了解离职原因。**

如果他平时表现比较好，而且在团队中承担比较重要的工作，我会考虑能不能挽留。

不过我也会尊重他的个人选择，同时了解是不是团队管理或者工作安排方面存在需要改进的地方。

**如果他确定要离职，我会尽快安排技术交接。**

会根据其他成员对项目的熟悉程度，选择一个比较合适的人来接手。希望在剩下的一个月里，让接替人真正掌握核心模块。

比如先把系统架构、关键代码、部署流程以及常见问题整理清楚。

然后安排两个人共同处理实际任务，逐步让接替人独立完成开发和问题排查，由原负责人进行指导和 Code Review。

**在这个过程中，我会定期检查交接情况，确认接替人能不能真正独立承担工作。**

如果发现技术难度比较大，或者一个月内可能无法完全掌握，我会提前向上级说明风险，看看能不能协调其他有经验的人员提供支持。

**同时，我也会重新评估现有项目的排期。**





**所以我不会一开始就要求他独立承担所有工作和风险。**

我会先和他沟通，了解他具体担心哪些地方，是技术上不熟悉，还是原来的任务太多，没有足够时间学习。

然后根据项目优先级，适当调整他原来的工作安排，尽量给他留出学习和交接的时间。

**同时，我们还有一个月的交接期，我会充分利用这段时间。**

安排原负责人带着他熟悉系统，从核心架构、关键代码到常见问题，逐步让他参与实际开发和问题处理。

在交接初期，我会继续负责整体技术把关和交付风险，不会把所有问题直接压到接替人身上。

**这个过程中，我也会定期检查交接进度。**

如果发现他的学习进度跟不上，或者这个模块确实超出了当前团队的能力，我会提前向上级说明情况，争取协调其他人员支持。

如果资源确实无法补充，我也会重新评估项目排期，看看能不能调整非关键任务，或者协商交付时间。



## 不配合

双方分别沟通，了解具体问题。

比如离职同事为什么不愿意配合，是交接工作太多，还是他觉得已经没有必要再投入太多精力。

接替人这边，我也会了解他目前到底卡在哪里，哪些东西已经掌握，哪些还不能独立处理。



因为只剩两周，我不会再要求把整个模块所有细节都交接完，而是**先保证关键部分**。

比如核心架构、部署流程、常见故障处理，以及目前还存在的风险。



**项目交付方面，我会重新评估剩余工作量。**争取先交付一个满足核心业务需求的版本。

**如果业务方不接受缩减范围，上级也坚持不能延期，我会把实际风险和资源缺口说明清楚。**同时给出我认为可行的交付方案，让有决策权的负责人明确取舍。







# 单点

现在回头看，虽然人力不足是客观情况，**我也应该更早意识到这种单点依赖的风险，提前安排必要的知识交接，而不是等到核心成员离职才处理。**

**我会先看哪些模块的单点依赖风险比较高，优先安排这些模块的知识共享。**

让不熟悉项目的同事，根据自己的理解去阅读和完善现有文档。

因为初学者比较容易发现文档里哪些地方讲得不够清楚，哪些步骤容易遗漏。

**后面也可以让他简单分享一下学到了什么、还有哪些地方不理解，再由原负责人补充和纠正。**

先确保关键模块至少有其他人能够完成基本的部署和故障排查。

**对于确实缺少人力的情况，我也会提前向上级反馈。**

比如说明哪些模块存在单点风险，如果关键人员请假或者离职，会影响哪些项目，以及目前需要什么资源支持。

如果可以增加人员，当然可以考虑招聘或者协调其他团队支援。

如果暂时无法增加人手，我也会通过调整部分低优先级任务，给关键模块的交叉学习留出一定时间。





**但我会进一步和他解释，单点依赖本身也是一种交付风险。**

**当然，我也不会要求所有人马上开始轮岗。**

我会先挑一个风险比较高的核心模块，看看能不能通过一个小范围的试点来验证效果。

比如让一位同事在正常开发过程中参与 Code Review，补充一些关键文档，再尝试独立完成简单的问题排查。

**如果上级还是不同意，我会尊重最终的资源安排，但会把风险和可能的影响说明清楚。**

在现有工作允许的范围内，我也会继续做好必要的技术文档和代码交接。

如果后续项目压力减轻，或者单点风险进一步增加，我会结合新的情况再次提出建议。



# KPI

**因为 GPU 成本优化是有上限的，不能直接认为只要优化推理性能，就一定能降低 30% 的费用。**

我会先看现在 GPU 的使用率、不同时间段的业务流量、模型部署情况，以及实际成本主要花在哪里。

然后再判断还有哪些优化空间。

比如推理服务本身有没有性能瓶颈，能不能通过优化提高单卡吞吐量，或者有没有一些低频服务在空闲时间仍然占用 GPU。

**如果发现还有优化空间，我会进一步评估投入产出。**

包括需要多少研发人力、预计多长时间完成、可能节省多少资源，以及会不会影响现有服务的稳定性。

像我们之前研究过 KEDA 自动扩缩容，就可以考虑针对一些低频服务，在没有任务时把 Pod 缩容到 0。

不过这也要结合实际情况，比如模型重新加载的时间、业务能不能接受冷启动，以及缩容以后能不能真正释放 GPU 节点成本。

**如果发现单纯的推理优化已经很难继续带来明显收益，我也会考虑从资源调度和部署方式上寻找机会。**

比如提高 GPU 资源复用率，减少低峰期的闲置，或者优化不同模型的资源分配方式。

在确定方案之后，我会根据实施成本、预期收益和风险安排优先级，先做投入比较小、收益比较明确的部分。

**对于 30% 这个目标，如果评估下来一个季度确实难以完成，我会提前向上级说明。**

我会把目前的成本基线、各项优化预计能节省多少，以及需要投入的人力和时间整理出来。

同时提出阶段性的优化目标，比如这个季度先落地哪些方案，预计实现多少成本下降，剩下的优化放到下一个阶段。





# 推广

**我会先去了解实际的业务场景，看看大家为什么不愿意使用。**

比如是 Agent 的结果不够准确，需要人工反复修改，还是整个操作流程比较麻烦，没有融入他们原来的工作方式。

也可能是我们一开始选择的业务场景就不太合适，实际需求没有想象中那么大。

**所以我会先和业务部门沟通，结合使用数据和实际用户反馈，找出主要原因。****如果确认是技术或者流程问题，我会优先选择影响比较大的部分进行优化。**

比如优化 Agent 的执行流程，减少人工操作，或者让它更好地接入现有业务系统。

改进以后，我会先找部分业务人员进行验证，对比优化前后的实际效果，而不是直接全面推广。

**如果验证下来确实能够提高效率，我会考虑继续投入和推广。**

但如果经过分析发现，业务需求本身就比较弱，或者继续优化的投入明显高于收益，我也会向上级说明情况，建议调整方向，必要时停止继续投入。



**不会马上建议停止，因为还需要了解它有没有长期战略价值。**

**同时，我也会从两个方面考虑改进。**

一方面是降低成本，比如分析模型调用费用、服务资源和维护工作量，看看有没有可以优化的地方。

另一方面是提高实际使用率。

我会先了解业务人员为什么不用，是功能不符合需求，还是使用流程太复杂，或者实际效果没有达到预期。

确认原因以后，再选择收益比较明确的部分进行优化，而不是盲目增加功能。

**如果业务方和上级都希望继续投入，我会建议先设定一个阶段性的验证计划。**

比如控制下一阶段的投入预算，明确要改善哪些指标，包括使用率、实际节省的人工时间、单任务成本，以及业务人员的持续使用情况。

经过一段时间验证以后，再根据实际数据判断项目是否值得继续扩大投入。

**如果效果确实有改善，长期收益也比较明确，那就可以考虑继续推进。**

但如果投入之后效果仍然不明显，我也会把成本、收益和实际使用情况如实反馈给上级，建议重新调整业务方向，或者缩小项目投入。

如果上级综合战略因素决定继续，我会按照确认的方向推进，同时把预算、阶段目标和风险说明清楚。



# 拿大结果

**但我也不会直接说这个目标不合理，而是先做一次具体评估。**

首先，我会分析目前使用率低的原因，以及实际的成本和业务收益。

比如是 Agent 的效果不够好，还是业务流程不合适，或者目标用户本身就没有太强的使用需求。

同时，我也会和业务部门确认，提高使用率需要他们提供哪些支持。

**我会把三个月的目标拆成几个阶段。**

第一个阶段先分析问题，确定优化方向和评估指标。

第二个阶段选择一两个价值比较明确的场景进行优化和验证。

第三个阶段根据验证结果，决定是否继续扩大推广。

**责任划分上，技术团队负责 Agent 的效果、稳定性、性能和成本优化。**

但使用率和最终业务收益，需要业务部门一起配合，包括需求调整、业务流程整合和用户推广。

对于我负责的技术工作，我可以承诺交付计划、质量要求和成本控制目标，并对执行结果负责。

**如果三个月之后没有达到预期，我也会承担自己负责部分的结果责任。**

我会分析到底是技术优化没有达到预期，还是业务使用情况和原来的判断有偏差，再结合实际投入产出，向上级提出继续优化、调整方向或者停止投入的建议。



我会全力争取，但现在没有足够数据，我不能直接保证一定达到。

**不过我能保证的是，我不会只是把项目接下来，然后到三个月结束才告诉你结果。**

我会先把影响使用率的关键问题找出来，和业务部门明确各自的责任，再把三个月拆成几个阶段，每个阶段都有具体的目标和验证结果。

如果中间发现某个方向效果不好，我会及时调整，而不是一直投入到最后。

预算方面我也会控制好，优先验证最有价值的部分。

**我认为选择我负责，不是因为我敢承诺一个不确定的数字，而是因为我能把不确定的目标拆解成可以执行、可以验证的计划，并且对推进过程和最终结果负责。**

如果最后没有达到目标，我也会拿出具体数据，说明差距在哪里、哪些判断需要改进，以及接下来应该怎么做。





# 最大变化

**以前做研发的时候，我更多关注的是技术问题怎么解决，代码怎么实现，性能能不能优化。**

但是作为技术负责人以后，我除了考虑技术方案本身，还要考虑实现成本，比如需要多少人、投入多少时间、有没有交付风险，以及其他部门能不能配合。

另外，工作方式也发生了变化。

以前主要是自己把任务完成，现在需要考虑怎么合理分工，哪些事情可以交给同事独立处理，哪些关键问题需要我来把关。

**还有一个比较大的变化，就是需要承担更多决策责任。**

很多时候信息并不是完全充分的，也没有现成的最优方案，但项目不能一直等。

这时候我需要结合目前掌握的信息，综合判断实现成本、收益和风险，必要时先做小范围验证，然后作出决策。

如果后面发现判断有偏差，也需要及时调整，并对自己负责的结果承担责任。



# 决策

**我会先安排一个技术能力比较合适的同事，花一两天做个小范围的 Demo 验证。**

其他成员还是继续推进原有方案，尽量不要因为新技术预研影响当前项目的交付。

验证的时候，我会先关注几个关键问题。



**同时，我也会结合业务未来的发展情况来判断。**

**等两天的验证结束以后，我会根据结果决定下一步。**

如果新框架收益比较明显，关键风险也能够控制，而且剩余的开发和测试时间足够，那可以考虑采用。

但如果还有很多不确定因素，我会优先保证这次项目使用现有方案按时交付，把新框架放到后续版本继续验证。

因为项目已经临近上线，不能为了追求理论上更好的性能，承担过大的稳定性和交付风险。





但我也会和业务方解释，**Demo 跑出来的结果，不代表这个框架现在就能够直接上线。**

因为 Demo 主要验证的是核心功能和性能，而正式上线还涉及系统集成、部署、监控、稳定性测试以及后续维护等问题。

现在工程师评估至少还需要三周，但项目只剩下 12 天，如果直接切换，延期风险和上线后的稳定性风险都比较高。

**所以我会先确认，原来的框架能不能满足这次上线的核心业务要求。**

**我也会把两个方案的收益和风险向业务方说明清楚。**

如果现在强行采用新框架，可能获得更好的性能，但需要承担延期和稳定性风险。

如果先采用原方案，可以保证当前交付，后续再通过充分验证逐步迁移。

如果业务方坚持必须本期使用新框架，我会把时间和技术风险明确反馈给相关负责人，重新确认交付要求和计划，而不是直接承诺 12 天内一定完成。



**我觉得这件事也需要我来负责跟进，不能因为一直有新需求，就让之前的优化计划完全没有下文。**

我会先重新评估新框架迁移的价值。

比如现有框架现在能不能满足业务要求，新框架的性能提升有没有实际业务价值，能不能减少资源成本，以及迁移还需要多少人力和时间。

**如果收益比较明确，我会整理出具体方案，再和业务方以及上级讨论优先级。**





**因为现在 GPU 利用率只有 35%，原有服务也能满足业务需求，所以我会先判断这个性能提升到底能不能带来实际收益。**

比如能不能减少 GPU 数量，节省多少资源成本，或者有没有明显改善用户的响应体验。

另外，还要考虑未来业务量会不会快速增长，现有框架有没有可能成为瓶颈。

**同时，我也会评估迁移的投入和风险。**

因为需要两名工程师投入一个月，这本身就有研发成本，而且迁移之后还需要测试和验证稳定性。

如果迁移带来的实际收益比较小，那这两个人可能还不如先投入其他优先级更高的项目。

**所以按照目前给出的条件，我会倾向于暂缓正式迁移。**
