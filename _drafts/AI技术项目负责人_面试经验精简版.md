# AI 技术项目负责人｜面试经验精简版

> 用途：面试前快速复习。优先讲**真实项目中的动作和结果**；后面的管理情景题是**遇到类似情况时的处理思路**，不能当作已经发生的经历。
>
> 核心表达：**先给判断 → 讲依据与取舍 → 说怎样组织执行 → 补充风险、结果和复盘**。不要只停留在“评估一下、沟通一下”。

## 一、自我介绍（中文，约 1 分钟）

我上一份工作是模型部署工程师，同时承担算法工程团队的技术负责人职责，主要做**模型推理优化、GPU 资源调度和 AI 服务工程化**。

技术方面，我主导过 Triton Inference Server 的选型和落地，通过共享内存、异步推理、前后处理并发等优化，在其中一个小模型服务压测中，把 QPS 从不到 3 提升到几百；也做过生图模型的缓存、`torch.compile` 和 CuPy 优化。

工程化方面，我主导过部署 SDK、MCP Server SDK 等建设，也从零搭建过统一的日志、链路追踪和告警组件，并参与基于 KEDA 的 GPU 自动扩缩容方案设计。

除了技术研发，我还负责约 5 人团队的**方案设计、任务分工、技术评审、进度跟进和跨部门协调**。我比较擅长把复杂技术方案落地成团队可以持续使用和维护的工程能力。

### English introduction（精简）

In my previous role, I worked as a Model Deployment Engineer and Algorithm Engineering Lead. My focus was **inference optimization, GPU resource scheduling, and AI service infrastructure**.

I led the adoption of Triton Inference Server and helped improve one small-model service from fewer than 3 QPS to several hundred through shared memory, asynchronous inference, and concurrent processing. I also worked on deployment and MCP Server SDKs, observability, and GPU autoscaling with KEDA.

Beyond hands-on engineering, I helped lead a team of around five, covering technical planning, task allocation, reviews, and cross-team delivery. My strength is turning technical solutions into reliable, reusable engineering systems.

## 二、团队管理方式（真实经历，约 45 秒）

我负责的团队大约 5 人，通常**按成员擅长的技术方向和项目需求分工**。项目启动时，我先确认业务目标、技术方案和主要风险，再拆分任务、明确负责人，并与算法、平台、前端、运维等相关团队对齐接口和排期。

执行过程中，我关注关键任务进度和阻塞，通过技术讨论、Code Review 保证质量。团队内部能解决的问题先协调处理；涉及跨部门依赖或交付变更时，我会**带着影响评估和可选方案**去沟通。重大技术问题我会参与把关，但成熟的常规工作尽量交给同事独立负责。

**管理边界：**我主要负责技术与研发交付层面的决策；涉及跨业务优先级、其他部门资源或对外交付日期的重大变更，需要与有相应权限的负责人确认。

## 三、Triton Server 真实项目（重点案例，约 2 分钟）

**背景与目标：**原来模型部署比较分散，希望通过 Triton 统一推理服务，提高性能和后续模型接入效率。整个团队约 5 人，但该项目**实际主要由我和另一名同事推进**；我负责总体技术方案、问题处理和项目协调。

**实施与验收：**我们按模型逐个迁移，与原服务、原始模型和测试集做对照，关注输出一致性；再通过不同并发量的压测，检查 QPS、延迟和资源表现。当时使用的内部相似度验收口径约为 99%（面试时要能解释该指标的具体定义）。

**问题与决策：**迁移中，我发现部分模型格式转换后输出误差较大，高并发时资源消耗也异常。我提出调整模型格式的方案，尽量不改动整体服务架构。根据剩余模型数及前面接入、验证的实际耗时，我估算还需要约一周，主动和算法部门沟通方案与延期。

**协作与风险控制：**不同模型需要各自算法负责人提供原模型、测试集和评估方式。为减少等待，我们一边运行已有验证脚本，一边提前沟通后续模型材料。两名项目成员分担问题，我也协助处理进展较慢的部分。**原有服务一直正常运行，因此迁移延期没有直接中断现有业务**；我们没有为赶时间跳过验收。

**结果与沉淀：**项目最终延期约一周，但完成了验收。之后基于已有代码框架，补充了模型接入、部署和常见问题文档，供算法、接入及运维人员使用，并在后续联调中完善。职责上由**算法准备模型与验证材料、我们负责接入、运维负责部署**。

**授权与后续：**流程稳定后，我把新模型常规接入和线上问题反馈交给之前参与项目的同事；我主要负责重大变更的 Code Review、复杂问题的技术方案和跨部门协调。有时我会先让同事提出方案，再一起评审，帮助他逐步独立承担工作。

**一句话总结：**我从亲自解决迁移问题，逐步转向**方案把关、任务授权、跨团队协调和流程复用**。这比单纯讲 QPS 更能体现技术负责人经历。

## 四、管理情景题｜高分回答要点（假设做法，不冒充经历）

### 1. 多项目并行、紧急需求或中途变更

**先保障线上稳定，再判断需求价值、剩余工作量和关键路径。**生产问题先查影响范围与趋势；如果风险可控，可以持续监控、安排后续修复。新需求要问清“为什么必须现在做、哪些是核心、能否分期”。保护原项目关键任务，优先内部协调；资源不够时，提供**缩范围、分阶段交付、调整日期**等备选方案，并写清各自影响。跨业务取舍由有权限的人确认，之后重新分工、同步排期。**不因压力盲目承诺，也不靠全员无限加班。**

### 2. 技术选型分歧、信息不足、Demo 很好但难落地

**先用统一标准比较方案，再给明确建议。**看性能、正确性、稳定性、研发人力、运维维护、团队熟悉度和交付窗口。存在关键不确定性时，安排一名合适成员做限时 PoC，其他人保留原交付路径。**Demo 跑通不等于生产就绪**，正式上线还要考虑部署、监控、集成、长期压测、灰度和回滚。如果旧方案满足本期要求，而新方案来不及验证，我倾向**本期用旧方案上线，后续再评估迁移**；但会记录迁移收益、投入、条件和重新评估时间，而不是口头说“以后再做”。

**技术债取舍：**性能提升 40% 不代表业务收益 40%。如果当前 SLA 已满足、成本不能实质下降，却要两个人月投入，我倾向暂缓；若现有方案将成为容量瓶颈或迁移能显著省钱，再提高优先级。

### 3. 线上事故与自己的技术决策失误

**先止损，再深入定位；明确分工，持续同步，验证恢复，最后复盘。**先看错误率、延迟、日志、Trace、Pod/GPU 状态和最近变更。影响较大且安全可回退时优先回滚；问题明确、可快速验证时考虑 Hotfix；必要时降级或切流。安排人员并行排障、执行恢复和业务验证，我负责综合判断及对外同步，不随意承诺恢复时间。

若事故与我主导的选型有关，我会**承担相应决策责任**，解释当时依据、哪些风险已知但验证不足，并推动补齐压测、灰度、回滚和复盘行动。若成员曾提前提醒，我会公开认可其判断，分析为什么没有采纳；重要异议要记录、验证，不能用职位压制不同意见。

### 4. 成员进度慢、能力差异与任务授权

**先诊断，不急着贴“态度差”标签。**综合过往表现、任务难度、工作量、Code Review 和本人反馈，看是能力、需求、估算还是依赖问题。单独沟通改进措施，让他先提方案、我来点评；同时保护项目关键路径，必要时拆任务或安排支援。观察后续进度与同类问题是否改善；若持续无法胜任关键模块，就调整分工。

**授权的边界：**常规工作让同事独立处理，重大变更和复杂 Bug 我参与 Review 或提供方案；跨部门障碍由我协调。目标是**让成员能独立交付，同时重要风险有人把关**。

### 5. 技术冲突、越级沟通与分工公平

**技术争论靠证据，不靠职位。**让双方给出同维度的成本、收益与风险；新证据可以重新评估，方案确定后明确负责人和执行要求。对越级沟通先了解原因，普通分歧鼓励先在团队评审，但重大安全或生产风险允许正常升级。方案更好就采纳并认可贡献，必要时授权其负责模块。

**人尽其才不等于特殊待遇。**复杂开发、文档、运维和协作都算贡献。综合工作量、难度、实际成果及成长机会判断是否公平；必要协作责任不能因为技术强就豁免，也要避免让其他人长期承担琐碎任务。

### 6. 核心成员离职、交接和单点依赖

先了解离职原因和挽留可能；确定离职后尽快指定接替人，**调整原有任务，给交接留出时间**。先交接关键架构、部署/回滚、常见故障、未解决风险；让接替人与原负责人共同处理真实任务，再逐步独立完成，由原负责人或我 Review。**交接要验收实际接替能力，而不是只看文档是否齐全**。若两周内无法全面掌握，就先保住关键维护能力，提前向上级说明资源缺口及交付风险。

日常则优先识别高风险单点模块，结合现有 Code Review、小任务、技术分享和**让初学者修改文档**来逐步培养备份人员。不要只等“有空再做”；也不要承诺完全零成本，需明确有限的投入和可验证效果。

### 7. GPU 降本 KPI 与投入产出

**先核实成本基线，再决定是否值得优化。**看 GPU 实际费用、流量峰谷、GPU/显存使用、模型部署密度、延迟和吞吐；区分性能优化与实际账单下降。KEDA 缩容 Pod 到 0 可能减少资源占用，但**如果 GPU 节点持续计费，未必真正省钱**；还要评估冷启动和 SLA。

按“预期节省金额—人力/时间成本—稳定性风险—回本周期”排序，优先做高收益低风险方案。如果 30% 目标缺少依据，主动向上级提出有数据支撑的阶段目标及缺口，而不是空口承诺。

### 8. AI Agent 技术达标，但使用率低、ROI 不好

**技术成功不等于业务成功。**先找业务人员了解不用的原因：准确性不足、人工复核多、流程麻烦、未接入现有系统，还是需求本来就弱。除了成功率、响应时间，还要看**持续使用率、业务任务完成率、人工修正时间、节省工时、单任务成本和净收益**。

选择高频场景做小范围对照验证，明确预算、阶段目标和继续/调整/停止条件。战略价值可以考虑，但也需要说明能形成什么可复用能力。若上级要求“三个月 10%→50%”，我不会无依据保证数字，却会承诺**阶段交付、预算控制、联合业务推进和及时纠偏**；最终未达标要解释数据、差距和下一步决策，而不是只讲客观原因。

## 五、角色转变（常见收尾题，约 40 秒）

以前做研发，我更多关注代码实现和技术问题；担任技术负责人后，我要同时考虑**人力、时间、成本、项目风险和跨部门依赖**。工作方式也从“我把任务完成”，转向“合理分工，让同事独立负责常规任务，自己把关关键决策并推进整体交付”。

技术决策常常信息不完整，但不能无限等。我会利用现有证据、小规模验证和可回退方案及时作出判断，发现偏差后调整并承担责任。**技术负责人不一定在所有领域最强，但要让团队的能力转化为稳定的交付结果。**

## 六、面试时记住的 6 句话

1. **先给判断，再说依据，最后讲执行与兜底。**
2. **我不只是发现问题，也会估算影响、提出备选方案并推动确认。**
3. **技术上能做，不代表当前业务上值得做。**
4. **Demo 有性能优势，不代表已经具备生产上线条件。**
5. **授权不是放手不管，而是常规工作独立推进、重大风险集中把关。**
6. **不盲目保证不可控结果，但对负责范围内的交付、预算、风险和纠偏负责。**

## 七、讲述边界（避免面试追问时失真）

- **团队约 5 人**，但 **Triton 迁移主要由 2 人实施**，不要说 5 人都投入该项目。
- Triton 延期约 **1 周**，是你根据剩余模型与既有接入经验估算并提出、与算法部门沟通；不要说成拥有对外延期的单方面批准权。
- “约 99% 相似度”是原项目的内部验收口径，**要说清具体计算指标**，不要自动等同于模型准确率。
- 原服务一直正常运行是迁移期间的**实际兜底条件**，不要无依据说成自己设计了复杂的双活容灾架构。
- 文档与交接形成了实际的协作分工；没有统计结果时，不要虚构“接入效率提升 X%”。
- 第四部分的管理题是**假设情况下的建议处理方法**；只有 Triton 等经过亲历的事情才能说成“我当时就是这样做的”。
